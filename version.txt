1.3.0   # Release version: the installer reads this first token. Set it with package.json and package-lock.json (see RELEASING.md).

Release Notes - 1.3.0

Summary
LaunchBridge is a set of AI coding agent skills, plus a CLI installer, that gives an agent working on a codebase persistent context, guardrails and tooling: codebase and artifact Q&A, governance files, a config and prompt registry, tests, prediction runs and evaluation, data preparation, and cost and latency reporting. It runs on the developer's workstation under the developer's own AWS credentials and calls Amazon Bedrock in that account. It is sample code for proof-of-concept and non-production use. 1.3.0 adds a global install, which puts the skills in each agent's user-level skills folder once for every project, and makes symlink installs link whole skill folders, which Codex needs.

What's New
- Global install: after the agents, the installer asks whether to install globally (the default) or into the current repository. A global install puts the skills in each agent's user-level skills folder (~/.claude/skills, ~/.kiro/skills, ~/.cline/skills, ~/.roo/skills, and ~/.agents/skills for Codex, Pi and other agents) and changes no repository. The first time lb-setup runs in a repository it checks that the folder is safe to prepare, then creates .lb_workspace/, .project_artifacts/, AGENTS.md (or AGENTS_LB.md to merge) and CLAUDE.md there from files the installer generated for it, and builds .venv_lb as before. It refuses a repository that has a local install
- --scope global|local skips the new prompt. Without it, the default is Local in a folder that already has a local install, whose agents are pre-checked, so a re-run there, --yes included, updates that install; anywhere else it is Global
- Installing locally (--scope local) in a repository lb-setup prepared for the global install says it is switching the repository and keeps the setup done there: lb-setup builds .venv_lb again only when the Python dependencies change, and offers the AGENTS.md merge when the installer stages AGENTS_LB.md. While the global install exists, Claude Code and Cline still run its lb-setup there, which refuses a repository with a local install: run lb-setup from Kiro or Roo Code (installed locally for it), or remove the global install
- The global install record (version, agents, method, selected skills, digests) is kept in ~/.config/launchbridge/global/, outside every repository, with the files lb-setup prepares repositories from beside it in generated/ (one copy for every agent). verify_integrity.py --global checks the installed skills and those files against it, and says how to fix each kind of difference it finds; lb-setup runs it on every run
- A global install that is interrupted, or can't write its record (it then exits 1), is finished by running launchbridge again, choosing Global and selecting the same agents and skills. Just before it replaces or creates a skill folder, a global install lists it in pending.json beside the record, which keeps only the folders it did not finish once the record is written; the next run treats those folders as LaunchBridge's, so it replaces them, a half-copied one included, even with --yes, and records them, and it names those it leaves listed because their agents or skills are not selected. A global install stops without installing anything when it can't write to that folder or can't read a pending.json there, and removes a new skill folder whose copy fails rather than leaving it half-copied
- launchbridge update, run from any folder, also brings a global install up to date: changed skills are copied again in a copy install (a symlink install's links already show them), missing skill folders are restored, lb-setup's generated files are regenerated, and each repository picks up the changes the next time lb-setup runs there. It updates the global install only from the clone that install came from, leaves an edited copy (whether or not the skill changed), a real folder where a link should be, or an agent's skills folder that is gone as a whole as it is, and keeps a skill the clone has uncommitted changes to at its recorded version (copying nothing for it and making none of its links again), and the generated files too while AGENTS.md or the dependency files they are built from have such changes. When git can't tell, it takes nothing new from the clone and exits 1. It says which, and how to fix each
- In a global install, Codex, Pi and other agents share ~/.agents/skills, which holds one form of each AI skill: Codex's when Codex is selected. The installer says which. Two agents whose skills folders are one folder through a link (a ~/.kiro/skills linked to ~/.claude/skills) can't both be selected
- The installer warns, before it asks to proceed, about selected skills the LaunchBridge clone has uncommitted changes to, and about such changes to agent_steering/AGENTS.md and the dependency files lb-setup's files are built from: they are installed as they are
- A skill deselected in a --yes run is left in place and stays recorded while its folder holds what LaunchBridge installs: the next interactive run offers to remove it, and selecting it again takes it back. Once the folder differs, it is treated as yours: it is not offered again, and a --yes run that selects the skill again leaves it and reports it. The results line counts as removed only the folders actually removed
- Symlink installs link each skill folder to its folder in the LaunchBridge clone (a junction on Windows, which needs no Developer Mode) instead of linking each file, so a skill always holds what the clone holds, including files it gains. Codex skips a skill whose SKILL.md alone is a link, so it now sees symlink-installed skills. An AI skill that an agent gets its own SKILL.md for is copied for that agent
- Older Kiro IDE and Cline releases don't load a skill folder that is a link: a symlink install for Kiro or Cline warns before it installs, and if the skills don't appear there, install again with --method copy

Skills
- lb-setup (setup and integrity checks): prepares a repository for a global install (Step G, bootstrap_workspace.py) and checks a global install with verify_integrity.py --global
- code-guardrails takes your own best-practices docs from the project, as best_practices_<name>.md in .lb_workspace/guardrails/, never from its installed folder, which a global or symlink install shares with every project. operational-metrics no longer says to add the Bedrock rates you supply to its own pricing file; they go only in .lb_workspace/operational_metrics/bedrock-pricing-overrides.md
- indexing-and-qa, config-prompt-registry, testing-framework, generate-predictions, evaluate-predictions, operational-metrics and ai-workflow find their files in a global install too
- Unchanged from 1.2.0: data-wrangler, comparative-metric-analysis and feature-recommendations
- After an update, a local install's lb-setup holds the changed skills back until you review them and refresh the digest baseline (verify_integrity.py --write-baseline)
- Optional AI skill bundles from aws-samples/sample-ai-skills (pinned at v0.6.2), one per domain: AI Spec-Driven Development (with the ai-workflow orchestrator), AI Architecture Decisions, AI Agent Context, AI Development Process, AI Prose Documents and AI Software Documentation; the release domain is not offered

Known Dependency Advisories (not yet fixed)
- The Python dependency set and the ai-skills pin are unchanged from 1.2.0, so its two advisories still apply: Pillow 12.3.0 in the optional ai-human-pdf skill (don't export documents that name an untrusted logo), and mcp 2.1.1 (GHSA-84m7-p3x7-pcfv, GHSA-5h93-6whr-6q8j, GHSA-w4fh-qvv9-3v23, GHSA-rwrf-2pqf-9j8j; not reachable, since every MCP server LaunchBridge registers runs over stdio and the Q&A launcher refuses IRIS's mcp_servers). See the 1.2.0 notes below for details

Upgrade Notes
- Requires Node.js 22.13 or later (^22.13.0 or >=23.5.0), npm, git and Python 3.12 or later
- Projects with a 1.2.0 local symlink install: after `launchbridge update`, run `launchbridge --scope local` again in each one before running lb-setup there. The update is run by 1.2.0's updater, which doesn't link files a skill gained, so lb-setup's new scripts/bootstrap_workspace.py is missing until the installer links the skill folder; lb-setup checks for it first and, until then, stops and says to re-run the installer. Copy installs are copied again by the update and need nothing more
- The next launchbridge run replaces each skill folder an older symlink install made of per-file links with a link to the folder (or, for an AI skill an agent has its own SKILL.md for, a copy), without asking when the folder holds nothing else; launchbridge update does it for the native skills. A folder that also holds files of your own is asked about first (a --yes run replaces it), and launchbridge update leaves it as it is
- If you put best-practices docs in code-guardrails' assets/best_practices/ folder, as 1.2.0 asked, move them to .lb_workspace/guardrails/ as best_practices_<name>.md before you update: launchbridge update (in a copy install) or the next launchbridge run can replace that skill folder, and 1.3.0's code-guardrails reads them only from the project
- Local installs work as before, and a re-run in a folder with a local install updates it. Keep one install for each repository: where a repository has a local install and a global one exists, Claude Code and Cline run the global skills and Kiro and Roo Code the local ones, and lb-setup from the global install refuses to prepare it. So once you install globally for Claude Code or Cline, lb-setup in those agents refuses every repository that has a local install: remove one of the two installs there (the User Guide says how), or set it up from Kiro or Roo Code when its local install is for them
- Whichever install it comes from, lb-setup stops in a folder that is not a project: the home folder, a folder above it, the file system root, or an agent's own folder (~/.claude, ~/.codex, ~/.kiro, ~/.cline, ~/.roo, ~/.agents) or a folder inside one. Open your agent in the project's own folder
- Scripts: in a folder with no local install yet, --yes without --scope installs globally; pass --scope local to make a local install. The installer now stops with exit code 1, before changing anything, on an argument it doesn't know or an option with no value, where 1.2.0 ignored them. launchbridge update exits 1 when it could not bring every install up to date
- LaunchBridge deploys no infrastructure; explicitly invoked AWS and Bedrock workflows may incur charges

Release Notes - 1.2.0

Summary
LaunchBridge is a set of AI coding agent skills, plus a CLI installer, that gives an agent working on a codebase persistent context, guardrails and tooling: codebase and artifact Q&A, governance files, a config and prompt registry, tests, prediction runs and evaluation, data preparation, and cost and latency reporting. It runs on the developer's workstation under the developer's own AWS credentials and calls Amazon Bedrock in that account. It is sample code for proof-of-concept and non-production use.

What's New
- Install with npm: `npm install -g github:aws-samples/sample-launchbridge` installs the launchbridge command. Its first run clones LaunchBridge into ~/.launchbridge, and every run installs from that clone, so symlink installs in every project share one copy and one `launchbridge update` updates them all. Installing from a clone with `npm run setup` remains for development and signed releases
- More AI skill bundles: the ai-skills library moves from v0.3.4 to v0.6.2, adding AI Architecture Decisions, AI Agent Context, AI Development Process, AI Prose Documents and AI Software Documentation alongside AI Spec-Driven Development
- `launchbridge update` reinstalls the CLI's npm packages (npm ci) when an update changes them, so an update that moves a dependency no longer leaves the CLI unable to start
- Symlink installs work when LaunchBridge is a git worktree or a submodule checkout
- Updated dependencies: inquirer 14 and chalk 6 in the installer; in the Python dependency set, Pillow 13.0.0, soupsieve 4.1.1, opentelemetry 1.45.2, tornado 6.6.1 and 52 other pins, which clears the Pillow and tornado advisories listed for 1.1.0. opencv-python stays below 5.1, whose first release ships Windows wheels only

Skills
- indexing-and-qa, code-guardrails, config-prompt-registry, testing-framework, data-wrangler, generate-predictions, evaluate-predictions, comparative-metric-analysis, operational-metrics, feature-recommendations, and lb-setup (setup and integrity checks)
- Optional AI skill bundles from aws-samples/sample-ai-skills (pinned at v0.6.2), one per domain: AI Spec-Driven Development (with the ai-workflow orchestrator), AI Architecture Decisions, AI Agent Context, AI Development Process, AI Prose Documents and AI Software Documentation; the release domain is not offered. On first use, the AI Prose Documents export skills fetch a Python 3.14 interpreter and pinned packages through uv, and ai-human-pdf fetches a pinned Mermaid renderer through npx when node is installed

Known Dependency Advisories (not yet fixed)
- Pillow 12.3.0 in the optional ai-human-pdf skill: the lock file that ships with its upstream script pins the same Pillow, which decodes the cover logo a document or the --logo option names. Don't export documents that name an untrusted logo until upstream updates it.
- mcp 2.1.1: GHSA-84m7-p3x7-pcfv (CVE-2026-59951, stateful Streamable HTTP server sessions), GHSA-5h93-6whr-6q8j (HTTP and SSE client redirects), GHSA-w4fh-qvv9-3v23 (HTTP server bearer-token audience) and GHSA-rwrf-2pqf-9j8j (client $ref fetches in tool output schemas). Not reachable: every MCP server LaunchBridge registers runs over stdio, and the Q&A launcher refuses IRIS's mcp_servers, the only way it would act as an MCP client. The fixed version (2.2.0) can't be installed yet because IRIS requires mcp<2.2.

Upgrade Notes
- Requires Node.js 22.13 or later (^22.13.0 or >=23.5.0), npm, git and Python 3.12 or later
- Upgrading a clone from 1.1.0: the CLI's npm packages moved from install_script/ to the repository root, and 1.1.0's updater doesn't reinstall them. After `launchbridge update`, `git pull` or checking out v1.2.0, run `npm run setup` once in the clone; launchbridge can't start until you do. Later updates reinstall changed packages themselves
- After updating, re-run the launchbridge installer in each project, then lb-setup in your agent: the Python dependency set changed, and lb-setup builds .venv_lb only from dependency files the installer recorded on this machine, and rebuilds a .venv_lb it didn't record
- LaunchBridge deploys no infrastructure; explicitly invoked AWS and Bedrock workflows may incur charges
